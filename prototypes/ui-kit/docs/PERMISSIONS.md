# Protoyard UI Kit: permissions

Simulated permissions: UX only, not security. Services enforce them with
`session.assert`, so a forbidden action fails even when the UI is bypassed.

## Record-level rules

<!-- protoyard:generated:rules -->
_No record-level rules._
<!-- /protoyard:generated:rules -->

There are no record-level rules. The favorites service needs no ownership
check because it only ever reads and writes the acting persona's rows
(`personaId` comes from the session, never from the caller).

Capabilities in `src/domain/policy.ts`:

- `favorites:manage` is named by no role, so only `designer` holds it
  (through `*`). `favorites.toggle` and `favorites.clear` assert it; the
  ☆ buttons and "Clear all" check it with `can()` to show a locked star
  with a tooltip, or hide the button, for a viewer.
- `favorites:read` is held by both roles but is not asserted anywhere: the
  favorites list is a direct `liveQuery` on the `favorites` table
  (`src/lib/favorites.svelte.ts`), filtered by the acting persona.

Everything outside favorites is open to every persona: browsing the
catalog, demos, the Forms page and the whole Theme Lab, including "Use in
prototype" and "Save draft as custom theme", which change the theme for the
prototype in this browser without any capability check. The header shows a
"Read-only" badge for the viewer.

## Persona switching

The persona is switched in DevTools (`Ctrl`/`⌘` + `.`), which is part of
`pnpm protoyard dev` but not of the static build
(`build.includeDevtools: false`). In a static build the scenario's actor is
the only persona: Dana Reyes in `default` and `empty`, Sam Ito in
`dark-viewer`.
