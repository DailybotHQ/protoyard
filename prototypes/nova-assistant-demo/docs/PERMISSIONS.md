# Nova Assistant: permissions

Simulated permissions: UX only, not security. Services enforce them with
`session.assert`, so a forbidden action fails even when the UI is bypassed.

## Record-level rules

<!-- protoyard:generated:rules -->
_No record-level rules._
<!-- /protoyard:generated:rules -->

There are none: the policy in `src/domain/policy.ts` defines no `rules`.
`rename`, `togglePin`, `setModel` and `moveToFolder` pass the conversation
to `session.assert`, but with no rules that changes nothing: any `owner` or
`member` can change any conversation.

What each capability guards today:

- `assistant:read`: `share`. Nothing else checks it; screens render for
  every role.
- `assistant:write`: `createConversation`, `send` (and voice sends),
  `regenerate`, `editMessage`, `feedback`, `setModel`, `rename`,
  `togglePin`, `createFolder`, `moveToFolder`, `updateCanvas`,
  `closeCanvas`.
- `assistant:settings`: `saveSettings`, `clearMemory`.
- `assistant:data`: `clearWorkspace`. Defined in `CAPABILITIES` but listed
  by no role, so only `owner` (through `*`) holds it; the matrix above
  cannot show it for that reason.
- `stop` has no check.

The UI never calls `can`: every role sees every control, and a forbidden
action fails in the service with the permission error shown in a notice
(or nothing, in the widget demo). Every scenario starts as Avery Stone
(`owner`); switch to Jordan Lee or Sam Rivera in DevTools to try the other
roles.
