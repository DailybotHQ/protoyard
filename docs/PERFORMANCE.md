# Performance

All numbers on this page were **measured in this repository**, with the
method stated. Nothing is extrapolated. Machine for every measurement below:
Apple M1 Max MacBook Pro (10 cores, 64 GB, macOS 27.0), Node 26.11.1,
pnpm 11.23.0. Each section states its date (2026-10-17 or 2026-10-18).

## Prototype bundles (production builds)

Method: `pnpm protoyard build --all` (DevTools excluded, the default). Every
build records its sizes in `build-manifest.json` under `bundle`, gzip level 9
per file: **initial JS** is the entry chunk plus everything it imports
statically (what a first page load downloads), **lazy JS** is every chunk
reached only through `import()`. `pnpm protoyard budget --all --skip-build`
reads those numbers and checks them. Measured 2026-10-18, after the merge of the eighth prototype (Vite 8.3.4):

| Prototype | Initial JS (gzip) | CSS (gzip) | Lazy JS (gzip, all chunks) | Largest lazy chunk (Faker) | Whole `dist` (raw / gzip) |
| --- | ---: | ---: | ---: | ---: | --- |
| `crm-demo` | 166 KB | 16 KB | 261 KB (40 chunks) | 150 KB | 1,452 KB / 561 KB |
| `mobile-banking-demo` | 197 KB | 16 KB | 185 KB (14 chunks) | 150 KB | 1,318 KB / 474 KB |
| `ai-chat-demo` | 196 KB | 16 KB | 185 KB (14 chunks) | 150 KB | 1,343 KB / 503 KB |
| `nova-assistant-demo` | 162 KB | 18 KB | 199 KB (20 chunks) | 150 KB | 1,157 KB / 380 KB |
| `support-widget-demo` | 144 KB | 15 KB | 185 KB (14 chunks) | 150 KB | 1,052 KB / 345 KB |
| `lattice-saas-demo` | 198 KB | 16 KB | 235 KB (38 chunks) | 150 KB | 1,361 KB / 450 KB |
| `relay-chat-demo` | 143 KB | 16 KB | 185 KB (14 chunks) | 150 KB | 1,054 KB / 345 KB |
| `helpdesk-demo` | 200 KB | 16 KB | 231 KB (33 chunks) | 150 KB | 1,384 KB / 451 KB |
| `ui-kit` | 182 KB | 16 KB | 375 KB (140 chunks) | 150 KB | 1,647 KB / 575 KB |

Every prototype is inside the 250 KB initial-JS and 30 KB CSS budgets
(`lattice-saas-demo` has the least headroom, about 52 KB). The table of
2026-10-17 counted a 14 KB chunk as "shared initial"; the build analysis
shows it is loaded through `import()`, so it is lazy. Earlier on 2026-10-18
`crm-demo` measured 202 KB initial; it is 166 KB after its screens moved to
lazy routes (`src/routes.ts`).

The archetype contract test resolves each selected kit through public package exports and
verifies the SaaS onboarding route is lazy. It does not build the player route registry, so
it adds no measured prototype chunk size. The 250 KB initial-JS budget remains the gate for
each generated prototype; per-archetype route measurements require player route integration
and a production build.

`helpdesk-demo` (generated by `protoyard generate` from a blueprint) was
measured on its own build the same day, from the `bundle` block of
`artifacts/helpdesk-demo/build-manifest.json` (204,347 B initial JS gzip, the
same 200 KB that `pnpm protoyard budget helpdesk-demo` reports). Every
entity screen and the hand-written ticket workspace are lazy route chunks.

**Generated world load (helpdesk-demo, `massive`).** Method: headless
Chromium (Playwright 1.64) on the production build served by
`pnpm protoyard preview helpdesk-demo`, a fresh context per run, opening
`?scenario=massive#/` and timing from navigation until
`html[data-protoyard-ready="1"]` and the dashboard counters render, with a
`longtask` PerformanceObserver. The world holds 600 tickets plus customers,
replies, audit entries and notifications. Three runs on 2026-10-18 (Apple M1
Max, macOS 27.0, Node 26.11.1): **252, 256 and 309 ms** to a rendered
dashboard, **0 long tasks** in every run. Not measured: real phones, and
larger worlds.

AI-era flagships (Nova, Relay) and refreshed kit builds are recorded under
[AI kits](#ai-kits). The `ai-chat-demo` row above is the 2026-10-17 baseline;
the 2026-10-18 rebuild in that section is the current measured value.

- **Faker loads only when a world is generated** (first seed, scenario load,
  reset or time advance) through a dynamic `import()`. Ordinary page opens
  never download it. Making it lazy cut the CRM's main chunk from 1,080 KB to
  666 KB raw.
- The biggest remaining contributors to the initial chunk (sourcemap
  analysis of the CRM build) are Svelte, zod, Bits UI, tailwind-variants and
  tailwind-merge, and Dexie, in that order.
- Each artifact contains only its own prototype's code. `protoyard export`
  checks this.

(2026-10-18, same machine, Node 26.11.1, pnpm 11.23.0, Vite 8.3.4 / Rolldown 1.2.13).
Each file is gzipped at level 9 with Node's zlib (no file name in the header). "Initial" is

## Versioned budgets

Workspace targets live in the root `protoyard.budgets.json`, separate from
prototype manifests. The file uses format `protoyard.budgets`, version `1`,
and supports partial per-slug overrides. When the file is absent, the CLI
loader uses the defaults below.

| Field | Default | Meaning |
| --- | ---: | --- |
| `initialJsGzipKb` | 250 KB | Initial JavaScript transfer size after gzip |
| `cssGzipKb` | 30 KB | CSS transfer size after gzip |
| `coldStartMs` | `null` | No calibrated threshold yet; report-only until set (see [Cold start](#cold-start-built-prototypes)) |
| `generateMs` | 50 ms | Scenario generation target |
| `indexColdMs` | 100 ms | Cold metadata-index target |
| `ideaToRunningMs` | `null` | Brief synthesis through first paint with a seeded world; calibrate before gating |
| `briefToBlueprintMs`, `blueprintValidationMs`, `prototypeGenerationMs`, `prototypeBuildMs`, `previewReadyMs` | `null` | Optional per-phase idea-to-running thresholds |
| `quickReadyMs` | `null` | `protoyard quick` brief → ready folder → `protoyard:ready`, no build (see [Quick exploration](#quick-exploration-brief-to-ready-measured-2026-10-20)) |

An optional `kinds` key holds the per-kind player entry budgets (ADR-040). When a
kind is missing, the loader uses the provisional defaults below; measured numbers
replace them once the deck, page and doc entries exist.

| `kinds.<deck\|page\|doc>` field | Provisional default | Meaning |
| --- | ---: | --- |
| `initialJsGzipKb` | 150 KB | Initial JavaScript of the kind's minimal player entry, gzip |
| `cssGzipKb` | 30 KB | CSS of the kind's player entry, gzip |
| `singleFileKb` | 1,536 KB (deck), `null` (page, doc) | Raw size of the kind's single-file export; `null` until calibrated |

These budgets are **enforced**:

| Budget | Gate | Fails with |
| --- | --- | --- |
| `initialJsGzipKb`, `cssGzipKb` | `pnpm protoyard budget <slug\|--all> [--skip-build]` | exit 4 |
| `indexColdMs` | `pnpm bench:index --runs 3 --check [--ci-factor 3]` | exit 1 |
| `generateMs` | `pnpm protoyard scenario bench <slug> --check [--ci-factor 3]` (CI multiplies the budget by 3 for slower runners) | exit 4 |
| `coldStartMs` | `pnpm exec tsx scripts/bench-cold-start.ts <slug…> --check` | report only while `null` |
| `ideaToRunningMs` and configured phase budgets | `pnpm exec tsx scripts/bench-idea.ts --runs 3 --check` | report only while `null`; exit 1 over a configured median budget |
| `quickReadyMs` | `pnpm exec tsx scripts/bench-idea.ts --mode quick --runs 3 --check [--ci-factor 3]` | report only while `null`; exit 1 over the median budget |
| Packed package parity | `pnpm verify:packages --budget-parity` | exit 1 when the packed consumer's initial JS gzip is more than 2 KB from the same blank-template source build, or above 250 KB |
| Data grid (thresholds in the script) | `pnpm exec tsx scripts/bench-grid.ts --rows 100000 --runs 3 --check` | exit 1 locally; report only on CI until calibrated there |
| Views kit chunks (`CEILINGS` in the test) | `pnpm vitest run packages/cli/tests/views-bundle.test.ts` | test failure (part of `pnpm test`) |

The `perf` job in [.github/workflows/ci.yml](../.github/workflows/ci.yml)
runs the first three on every pull request and push to `main`, and reports
cold start without gating it (see
[TESTING_GUIDE](TESTING_GUIDE.md#ci-performance-job-githubworkflowsciyml--perf)).

### Published package build parity

`pnpm verify:packages --budget-parity` extends the tarball consumer check. It
uses the packed CLI and packages to scaffold `second-app` from the published
blank template, then runs `protoyard budget second-app --skip-build` against
the production build already made by `validate --build`. It separately
scaffolds the same blank template from workspace source and runs
`protoyard budget` there, which builds and measures that source version.
The gate prints both initial-JS gzip values and their delta. It fails when the
absolute difference is over 2 KB or when the packed consumer exceeds the
250 KB initial-JS cap. Temporary source prototypes and build artifacts are
removed after measurement.

This parity check covers the blank starter only; it does not claim every
template has identical packed and source builds. The ordinary budget command
continues to enforce CSS for both builds as well.

Measured 2026-10-20 with `pnpm verify:packages --budget-parity`: the source
blank starter was **169.30 KB** initial JS gzip and the packed consumer's
starter was **169.20 KB**, a **0.10 KB** difference. Both passed the 250 KB
cap. The command also passed the tarball install, consumer scaffold/build,
gallery command and gallery build steps.

The bundle gate on this repository (2026-10-18, abridged to two of the eight
prototypes):

```text
$ pnpm protoyard budget --all
Prototype            Metric         Value               Budget              Headroom    Result
───────────────────  ─────────────  ──────────────────  ──────────────────  ──────────  ──────
lattice-saas-demo    initialJsGzip  198 KB (197.70 KB)  250 KB (250.00 KB)  +52.30 KB   PASS
lattice-saas-demo    cssGzip        16 KB (15.95 KB)    30 KB (30.00 KB)    +14.05 KB   PASS
crm-demo             initialJsGzip  166 KB (165.64 KB)  250 KB (250.00 KB)  +84.36 KB   PASS
crm-demo             cssGzip        16 KB (15.93 KB)    30 KB (30.00 KB)    +14.07 KB   PASS
```

For one prototype, set only the values that differ:

```json
{
  "format": "protoyard.budgets",
  "version": 1,
  "defaults": {
    "initialJsGzipKb": 250,
    "cssGzipKb": 30,
    "coldStartMs": null,
    "generateMs": 50,
    "indexColdMs": 100,
    "ideaToRunningMs": null,
    "briefToBlueprintMs": null,
    "blueprintValidationMs": null,
    "prototypeGenerationMs": null,
    "prototypeBuildMs": null,
    "previewReadyMs": null,
    "quickReadyMs": null
  },
  "overrides": {
    "crm-demo": { "initialJsGzipKb": 280 }
  }
}
```

The root file contains these defaults with an empty `overrides` object.
Budgets stay out of `protoyard.json` so performance targets can evolve
without changing the strict prototype manifest contract.

**Route-level code splitting (available):** `@protoyard/renderer-svelte`
`createRouter` accepts `load: () => import('./Screen.svelte')` per route.
`<Router>` shows `LoadingState` while the chunk loads and `ErrorState` with
retry on failure; eager `component` routes are unchanged. Use `load` for
secondary screens in multi-entity apps so they leave the initial chunk.
Flagship prototypes still ship mostly eager routes today — adopt `load` when
adding screens that would push initial JS over the 250 KB gzip budget. No
before/after gzip delta is recorded here until a flagship switches a real
screen to `load` (crm-demo validate --build still passes with eager routes).

**Possible next steps (not done):** zod's smaller `zod/mini` build for runtime
parsing; moving secondary crm-demo / generated-app screens onto `load`.

## Cold start (built prototypes)

Method: `pnpm exec tsx scripts/bench-cold-start.ts <slug…> --runs <n>`
serves `artifacts/<slug>/dist` (build first with
`pnpm protoyard build <slug>`) with the CLI's static server on an
OS-assigned port, then opens a **fresh** headless Chromium context per run
(1280×800) and reads two performance marks that `mountPrototype` sets, both
measured from navigation start:

- `protoyard:world-ready`: the runtime is open and the world exists.
- `protoyard:ready`: the first screen has rendered (`html[data-protoyard-ready="1"]`).

**First visit** starts with an empty IndexedDB, so the default scenario is
generated (Faker is downloaded lazily) and written before the app renders.
**Repeat visit** reloads the same context: the stored world is reused and
the HTTP cache is warm. Results go to `tmp/bench-cold-start-<timestamp>.json`
with every sample and the machine.

Medians of 5 runs on 2026-10-18 (Apple M1 Max, 10 cores, 64 GB, macOS 27.0,
Node 26.11.1, headless Chromium 156.0.8078.4, a local static server, no
network throttling, production builds without DevTools), after the build of
the bundle table above:

| Prototype | First visit: ready (world ready) | Range | Repeat visit: ready (world ready) | Range |
| --- | --- | --- | --- | --- |
| `crm-demo` | **115 ms** (95 ms) | 110–170 ms | **43 ms** (36 ms) | 41–44 ms |
| `mobile-banking-demo` | **130 ms** (101 ms) | 125–134 ms | **40 ms** (33 ms) | 39–42 ms |
| `ai-chat-demo` | **125 ms** (95 ms) | 122–129 ms | **39 ms** (32 ms) | 37–45 ms |
| `nova-assistant-demo` | **108 ms** (74 ms) | 106–114 ms | **39 ms** (32 ms) | 38–42 ms |
| `support-widget-demo` | **104 ms** (76 ms) | 101–110 ms | **39 ms** (30 ms) | 36–40 ms |
| `ui-kit` | **117 ms** (76 ms) | 115–125 ms | **45 ms** (34 ms) | 41–48 ms |

- Most of a first visit is building the world (generate, validate, write),
  not rendering: `ready` follows `world ready` by about 20 to 41 ms.
- An earlier run the same day measured crm-demo at 141 ms and
  mobile-banking-demo at 132 ms on first visit. Runs vary by a few tens of
  milliseconds on this machine, which is one reason the threshold is not
  set yet.
- **Not measured:** real phones, throttled CPU or network, a remote host, or
  a cold HTTP cache on repeat visits. No claim is made beyond this table.

`--check` compares both medians with `coldStartMs` (per-prototype overrides
apply) and exits `1` when one is over. While `coldStartMs` is `null` it
prints "not calibrated … reported only, not gated" and passes, as ADR-019
says. Setting the threshold is a separate decision: CI runners are slower
than this machine.

```bash
pnpm protoyard build crm-demo
pnpm exec tsx scripts/bench-cold-start.ts crm-demo --runs 5 --check
```

## Idea → running prototype

Method: `pnpm exec tsx scripts/bench-idea.ts --runs 3` creates a disposable
workspace under `tmp/` for each run and install mode. It synthesizes a
blueprint from the same fictional field-service brief, validates it, generates
the prototype, builds it, then serves the static build on an OS-assigned port
in a fresh headless Chromium context. The `install` mode includes the
generator's offline workspace install. The `no-install` mode first links
dependencies in a separate offline setup step, then runs generation with
`--no-install`; that setup is outside the timer. The final phase ends when
`protoyard:ready` appears after the runtime's `protoyard:world-ready` mark
reports a seeded first world. The overall clock starts immediately before
blueprint synthesis; human brief review and editing are outside this automated
measurement. Results include per-phase medians and samples in
`tmp/bench-idea-<timestamp>.json` with the machine details.

The total and phase thresholds are nullable until calibrated. Set
`ideaToRunningMs` from a repeatable local median (the plan proposes 1.5×
that median); optional phase values can locate regressions. `--check` reports
when a budget is null and exits `1` if a configured median is exceeded. When
`CI` is set, `--ci-factor` (default `3`) scales configured thresholds.

First local comparison on 2026-10-19: 3 runs per mode on an Apple M1 Max
(10 cores, 64 GB, macOS 27.0, Node 26.11.1, Chromium 156.0.8078.4). A
background browser session was active, so treat these as an initial
calibration. All six runs reached a seeded first world. The JSON report was
written under the ignored `tmp/` directory during measurement.

| Phase | Install mode median (range) | `--no-install` median (range) |
| --- | ---: | ---: |
| Brief → blueprint | 754 ms (730–772 ms) | 726 ms (647–777 ms) |
| Blueprint validation | 680 ms (658–691 ms) | 638 ms (615–640 ms) |
| Prototype generation | 3,367 ms (3,359–3,479 ms; install included) | 1,355 ms (1,267–1,521 ms) |
| Production build | 33,601 ms (33,440–34,059 ms) | 37,882 ms (33,577–39,205 ms) |
| Preview ready with seeded data | 618 ms (607–619 ms) | 595 ms (592–606 ms) |
| **Idea → running** | **39,020 ms (38,794–39,619 ms)** | **41,008 ms (36,950–42,699 ms)** |

PLAN_003 Harborlight dogfood run on 2026-10-20 took **330,326 ms** from the
first brief review to the first passing production build. It ran on Darwin
27.0.0 arm64 with Node 26.11.1. This is one manual end-to-end observation,
including blueprint review/refinement, and it stops at build rather than the
benchmark's seeded preview-ready mark; do not compare it with the automated
medians above or use it to set a budget. The prototype's initial JS gzip was
201.53 KB (250 KB budget) and CSS gzip was 21.87 KB (30 KB budget).

The plan's 1.5× calibration rule suggests a local total ceiling of 58,530 ms
for the default install mode. The owner-held `protoyard.budgets.json` remains
uncalibrated (`null`); the lead can propose that value there after confirming
the integrated main result.

```bash
pnpm exec tsx scripts/bench-idea.ts --runs 3 --check
```

## Brief synthesis by kind (measured 2026-10-21)

Method: `pnpm exec tsx scripts/bench-brief-kinds.ts --runs 3` runs eight
fictional briefs, two each for app, deck, page and doc, through
`blueprintFromBrief` without a forced kind. That exercises kind detection plus
the app archetype path or a content synthesizer. Each run is the median of 50
calls after one warm-up call, and the table gives the median across runs. It
also records:

- the output size (blueprint JSON, raw and gzip);
- whether the output validates through `safeParseAnyBlueprint`;
- whether the deck layout catalog is in the synthesizer's import graph or in
  the built player's initial chunks.

Results and machine details go to `tmp/bench-brief-kinds-<timestamp>.json`
(format `protoyard.bench-brief-kinds`, version 1). The benchmark is
**report-only**: there are no budgets yet.

Apple M1 Max, macOS 27.0, Node 26.11.1, two consecutive runs agreeing within
noise:

| Kind | Median synthesis | Largest output | Detected | Validates |
| --- | ---: | ---: | --- | --- |
| app | 0.31 ms | 3,469 B | 2 of 2 | 2 of 2 |
| deck | 0.05 ms | 747 B | 2 of 2 | 0 of 2: the deck body schema is not wired yet |
| page | 0.06 ms | 2,184 B | 2 of 2 | 0 of 2: the drafts lack `page.id` |
| doc | 0.12 ms | 1,879 B | 1 of 2 | 0 of 1: the draft lacks `doc.id` |

- **Cost:** synthesis is far below a millisecond for every kind, so it never
  matters next to install, build or the player boot. Loading the brief modules
  for the first time (`moduleLoadMs`, tsx transpiling on first import) was
  about 1.4 s in this measurement.
- **Layout catalog:** the brief synthesizer's import graph (13 modules) imports
  only `@protoyard/core`, `@protoyard/scenarios` and zod, with no
  `@protoyard/decks` and no layout catalog. The player's initial chunks do not
  contain the layout catalog either. Authoring data does not inflate runtime
  entries.
- **Findings for the authoring lane** (recorded, not fixed here):
  - "Write a one-page report on…" is detected as an app.
  - Synthesized page and doc drafts fail their now-wired body schemas on a
    missing body `id`.
  - Decks validate only once the deck body schema ships.

## Data grid at 100,000 rows

Method: `pnpm exec tsx scripts/bench-grid.ts --rows 100000 --runs 3`
builds ui-kit (`--skip-build` reuses `artifacts/ui-kit/dist`), serves it with
the CLI's static server on an OS-assigned port, and opens a **fresh**
headless Chromium context per run (1280×800) on the grid demo
(`#/c/grid`, `prototypes/ui-kit/src/demos/views/GridDemo.svelte`). There it
presses **Load 100,000 rows**. The demo builds those rows in memory in the
page, not in IndexedDB, so the bench measures the grid's rendering and
virtualization, not storage or scenario generation. The rows are the demo's
own simple generator (`Record N`, three teams, a score), not a views
scenario fragment, and `--rows` accepts only the demo's 100,000. Per run it
records:

- **First render:** milliseconds from the click to the first painted frame
  where the grid reports every row (`aria-rowcount`) and shows its first
  data row. This includes building the 100,000 row objects.
- **DOM rows:** `[role="row"]` elements in the grid (header included) after
  that render, and the most seen during the scroll.
- **Scroll:** a scripted 5-second scroll from top to bottom (one
  `scrollTop` step per animation frame). It counts long tasks
  (`PerformanceObserver` `longtask`, all of them and those over 200 ms) and
  dropped frames (frame gaps beyond one 60 Hz interval, counted in missed
  intervals). A run that never renders the last row (`Record 100000`) fails
  the check.

Results go to `tmp/bench-grid-<timestamp>.json` with every sample, the
thresholds and the machine. Medians of 3 runs on 2026-10-19 (Apple M1 Max,
10 cores, 64 GB, macOS 27.0, Node 26.11.1, headless Chromium 156.0.8078.4,
a local static server, production build without DevTools, other build and
test jobs running at the same time, load average about 70):

| Metric | Median (range) | Threshold (`--check`) |
| --- | --- | --- |
| First render, 100,000 rows | **94 ms** (93–102 ms) | ≤ 500 ms |
| DOM rows (most seen while scrolling) | **17** (13 after the first render) | ≤ 80 |
| Long tasks during the 5 s scroll | **0** (none over 200 ms) | 0 over 200 ms |
| Dropped frames during the scroll | **0** of 301 frames (longest frame 17 ms) | reported only |

- An earlier run the same day with a reused build measured 91 to 98 ms for
  the first render, with the same row and frame counts.
- **Not measured:** real phones, throttled CPU, a headed browser on a
  high-refresh display, wide column sets, sorting or filtering 100,000 rows,
  or rows from IndexedDB. No claim is made beyond this table.

`--check` exits `1` when a median is over its threshold (`THRESHOLDS` in
the script). With `CI` set it reports and passes until the thresholds are
calibrated on a CI runner (`CI_CALIBRATED`), like `coldStartMs`.

```bash
pnpm exec tsx scripts/bench-grid.ts --rows 100000 --runs 3 --check
```

## Large worlds (scenario loads)

Measured with the `crm-demo` **`enterprise-scale`** scenario: **16,075 rows**
(300 companies, about 900 contacts, about 3,000 deals, more than 8,000
activities, plus identities), with zero integrity violations. Machine:
Apple M1 Max (64 GB, macOS 27.0), Node 26.11.1, Dexie 4.4.6. Medians of
3 runs, with ranges.

**Strategy.** The world is written in a **single read-write transaction**, so
a load is atomic: a failure in a later chunk leaves the previous world
byte-identical, and this is tested. Inside it, rows go in through
**chunked `bulkAdd`** (default 1,000 rows per chunk). Phases
(generate → validate → write) yield to the event loop between them, and
progress is reported per chunk (`onProgress`, `scenarios.subscribeProgress()`).
DevTools and the app shell show a progress bar.

| Environment | Generate | Validate | Write | Total `load()` | Long tasks |
| --- | --- | --- | --- | --- | --- |
| Headless Chromium 156, production build, chunk 1,000 | 26 ms | 10 ms | 477 ms (470–478) | **628 ms** (626–628) | **0** |
| Headless Chromium, single `bulkAdd` per table | 26 ms | 10 ms | 478 ms | 633 ms | 1 (85 ms) |
| Node + fake-indexeddb, chunk 1,000 | 21 ms | 9 ms | 417 ms (414–433) | — | — |

- Chunking doesn't change throughput (about 34 rows/ms in Chromium). It does
  remove main-thread stalls: zero long tasks at every chunk size from 250 to
  2,000, compared with an 85 ms long task and 67–83 ms frame gaps for a single
  `bulkAdd`.
- Generation and validation are cheap. Writing dominates.
- **Not measured:** real mobile devices, and worlds larger than about 16k rows.
  No scaling claim is made beyond what is in this table.


## Player worker generation

The player sends the validated blueprint and resolved scenario data to a module
worker for world generation. The worker creates its own `GenerateContext` and
returns the serializable `WorldSeed`; if workers are unavailable or fail, the
same generation helper runs from a lazy main-thread chunk. The worker/fallback
parity test compares five catalog blueprints across all four default scenarios.

**No Faker on the main thread.** A definition may provide
`generateWorld(scenario)` next to `generate(ctx)`. The runtime then calls it for
every scenario load, reset and stale-world reseed, with the effective scenario
(seed, preset and knobs applied), and never builds a `GenerateContext` for
them. The player's `withWorkerGeneration` supplies `generateWorld`, which
only posts the blueprint and scenario to the worker. `generate` stays as the
fallback and for `advance()` timelines; blueprint definitions declare no
timeline. Measured 2026-10-20 with the built player in headless Chromium
(`?src=./blueprints/quick/analytics.json`, until `data-protoyard-ready`),
comparing a build without the hook to the build with it:

| Build | Main-thread Faker chunk fetched | JS fetched by boot (page + worker), gzip |
| --- | --- | --- |
| before (`generate` only) | yes, 149.5 KB gzip | 752.7 KB (118 requests) |
| after (`generateWorld`) | **no** | **603.2 KB** (117 requests) |

Initial JS is unchanged: **177.9 KB** gzip in 25 chunks in both builds,
because Faker was never in the static graph, only dynamically imported at boot.
The main-thread Faker chunk still ships in `dist/`. It loads only if the worker
fails and the lazy main-thread fallback runs.

**Worker size.** The first build of the worker (Vite's default worker format)
inlined its dynamic imports. That kept the whole `@faker-js/faker` namespace,
every locale included: one `generate.worker` file of **2,555,194 B raw /
942,931 B gzip** (gzip level 9). The player now builds workers as ES modules
(`worker: { format: 'es' }` in `packages/player/vite.config.ts`). The worker then
code-splits and tree-shakes like the app, keeping only `Faker`, `en` and `base`.

Its whole import graph, measured 2026-10-20 (Vite 8.3.4, gzip level 9):

| Chunk | Raw | Gzip |
| --- | --- | --- |
| `generate.worker` entry | 496 B | 308 B |
| blueprint generator | 156,202 B | 45,407 B |
| scenarios context | 2,396 B | 1,288 B |
| Faker, English only | 416,073 B | 153,201 B |
| **Total** | **575,167 B** | **200,204 B (195.5 KB)** |

That is **79% less** than before, and no other locale's data ships (German and
Japanese markers are absent). The worker is a separate Rollup build, so its
Faker chunk is a second copy of the app's. A normal boot downloads only the
worker's copy; the app's copy is fetched only by the main-thread fallback.

**Main-thread long tasks during boot.** Measured with the built player in
headless Chromium, fresh context, `?src=` blueprint, 2026-10-20, with machine
load average about 40:

| CPU | Blueprint | Ready | Long tasks before ready |
| --- | --- | --- | --- |
| unthrottled | demo, quick/assistant, quick/team-chat (3 runs each) | 170 to 260 ms | none |
| 4× throttled | demo (2 runs) | 524 to 572 ms | 3, total 227 to 242 ms |
| 4× throttled | quick/assistant, quick/team-chat (2 runs each) | 469 to 487 ms | 2, total 172 to 182 ms |

Long-animation-frame attribution (4× throttled, quick/assistant):
- **About 100 to 130 ms evaluating the initial entry script.** This is not
  generation.
- **About 75 to 85 ms in Dexie** inside `IDBTransaction.oncomplete`, while the
  seeded world is written.
- **Neither is Faker:** its main-thread import never appears as a long-frame
  script.

So generation itself stays off the main thread. But "the main thread stays free
of long tasks" holds only on a fast CPU. On a 4× slower CPU, boot still has 2 to
3 long tasks from entry evaluation and the IndexedDB write. (These runs predate
`generateWorld`: each one also downloaded and evaluated Faker on the main
thread, only to build a context that the worker path ignored. That no longer
happens; the long-task table was not re-measured.)

## Player world cache (measured 2026-10-20)

The player keeps generated worlds in `protoyard.player.worlds` (IndexedDB),
keyed by the blueprint's SHA-256, the scenario id, seed and digest, and the
generator version (`packages/player/src/cache/`):
- **Format:** gzip of the world JSON.
- **Read limits:** read back with the snapshot import limits (25 MB inflated,
  250,000 rows).
- **Eviction:** least recently used past 48 MB of compressed data.
- **Writes:** compressed in 64 KB slices that yield between tasks. The runtime
  gets the world first and never waits for the write.

The table below comes from a headless Chromium (Playwright) Chrome trace of the
built player, with main-thread `RunTask` slices over 50 ms counted as long tasks.
The trace was checked with a 120 ms busy loop, which shows as one 120 ms long
task. Two runs at load average about 40, same results:

| --- | --- | --- | --- |
| Demo (4 entities) | First visit, seeds `active` | 221–238 ms | 0 |
| Demo | Reload (stored world, no generation) | 92–105 ms | 0 |
| Demo | Switch to `empty` (generate) | 54–55 ms | 0 |
| Demo | Back to `active` (cache hit) | 10–12 ms | 0 |
| Demo | Switch to `massive` (generate) / cache hit | 60–61 ms / 28–29 ms | 0 / 0 |
| Large fixture (40 entities, 997 fields) | First visit | 364–408 ms | 0 |
| Large fixture | Back to `active` (cache hit) | 59–64 ms | 0 |
| Large fixture | Switch to `massive` (generate) | 1,368–1,429 ms | 1 (55–56 ms) |
| Large fixture | `massive` again (cache hit) | 901–915 ms | 0 |

| interaction (InteractivePlot, Axis, Grid, Tooltip, model) | 3,727 |
| frame | 2,015 |
| scales | 1,897 |
| downsample | 924 |
| shapes | 885 |

The structural options proposed for the 10 KB target cannot reach it on
their own:
- Removing the whole interaction layer would still leave about 12.2 KB.
- A lighter InteractivePlot for single-series charts could save only part of
  its 3.7 KB, while multi-series charts would keep the full one.
- Merging Axis and Grid into the plot saves component boilerplate, not their
  logic.

These were not prototyped. Reaching 10 KB would mean cutting chart features
(keyboard model, tooltip, axes formatting) or the scales and frame, and the
plan's accessibility contract rules that out. 16,006 B is the honest number,
held under 17,000 B by the guard.

## Runtime behavior worth knowing

- **Reads are reactive and scoped.** `liveQuery` re-runs only when the tables
  a query touched change.
- **Writes are transactional.** Scenario loads write the whole world in one
  transaction (clear, then insert). The UI shows the result when it commits.
- **Per-origin storage quota.** Every prototype opened from the same origin
  shares the browser's quota. `runtime.storage()` reports usage and quota
  when the browser exposes them.
- **The dev server is per prototype.** `protoyard dev <slug>` starts Vite for
  one app only, so HMR cost doesn't grow with the number of prototypes.

## CLI integration startup and protocol budgets

`pnpm exec tsx scripts/bench-integrations.ts --runs 3` measures three local
process boundaries without building a prototype or starting a network server:

- **Doctor startup:** a fresh Node + tsx process runs `doctor --json --offline`
  through exit, and the benchmark verifies the successful machine-readable
  envelope.
- **MCP startup:** a fresh `protoyard mcp` process starts and answers the
  stateless `server/discover` request over stdio.
- **MCP round trip:** the same process answers a `tools/call` for offline
  `doctor`; the benchmark checks the JSON text envelope and then closes stdin.

The report records each sample, the median, machine details, and the pass/fail
result in `tmp/bench-integrations-<timestamp>.json`. It exits nonzero when a
median exceeds these local ceilings:

| Measure | Median budget | Three-run baseline |
| --- | ---: | ---: |
| Doctor startup and check | 10,000 ms | 3,642.1 ms |
| MCP startup to `server/discover` | 4,000 ms | 2,189.6 ms |
| MCP `doctor` tool round trip | 5,000 ms | 1,459.4 ms |

Baseline measured 2026-10-20 on Apple M1 Max, 10 cores, Node 26.11.1. The
ceilings are rounded above the observed samples (maximums: 3,675.2 ms,
2,291.2 ms, and 1,767.2 ms respectively) to leave headroom for local variance.
They are local development thresholds, not a claim about other machines; run
the same benchmark on a CI runner before tightening or treating them as CI
service-level guarantees. Keep the MCP transport lazy: `commands/mcp.ts`
imports the stdio server and tool registry only when `protoyard mcp` runs.
`packages/cli/tests/integration-performance.test.ts` guards the median budget
calculation and that lazy import boundary.
